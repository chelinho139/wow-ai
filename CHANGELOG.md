# Changelog

All notable changes to this project are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- Per-plugin model and effort: `plugins.<id>.agents.<agent>.model` and `.effort` override `agents.<agent>` for that plugin's chats, under a chat's own `--model` / `--effort`. Quick in-game questions (`ask`) can run on a fast model while coding chats keep a max-effort default. Only `model` and `effort` are read from the block. See docs/CONFIGURATION.md.
- Classic Era support. The addon and the slot addons declare `## Interface: 11509, 16001`, so they load in Classic Era 1.15.9 as well as in WoW Forever. The situation block says `Game: World of Warcraft Classic (client 1.15.x, interface 115xx)` there, and the system prompt says that Classic web databases describe it while the synced Forever data does not (wowdata answers are labeled build-mismatch, reference tokens are refused). `claude-wow setup --wow <client folder>` on an existing config now points it at that client (`addonDir`, `inboxFile`, `savedVariablesFile`, `capture.processName`), and setup replaces the old `tocInterface` default `"16001"`. The addon primer has a Classic Era line. On Classic Era the chat window draws only the atlases that client uses (parchment, gear, turn-in icon); the Forever quest-log atlases exist there by name but have no texture and drew as a solid green box, so plain fills replace them. Every Forever-only call the addon makes was already guarded; the check is the `classic_era` and `forever` branches of wow-ui-source plus `strings` on both client binaries.
- Game names in orders now come from the synced Forever data. `order_issue` takes reference tokens (`{item:ID}`, `{skill:ID}`, `{map:ID,x,y}`); the bridge expands them to canonical names from `client-data` rows for the client's build family, stores the expanded text with its `refs`, and pushes that text to the overlay. A map token shows the map's name only; its x and y are kept in the ref with `trust: "model"`. An unknown ID, a malformed token, a token glued to a letter, a digit or another token, a kind with no name source (`{npc:ID}`, `{quest:ID}`, `{faction:ID}`) or a data name with a character outside the order set refuses the whole order with the reason per token. With no synced data, another build family or no client build, tokens are refused and the error says only reported names work; plain orders behave as before. The word allowlist still runs on the text around the tokens, and the 90-character cap applies after expansion.
- Multi-word game names made of plain words ("old town", "back stab") are caught by a phrase check on orders and the roast card. Every run of 2 to 4 words inside one clause is refused when it is an area, map, flight path or skill line name in the synced data, a spell a spell-book, recipe, rune or tablet item teaches, or in a short built-in list of ability and place phrases made of plain words (`bridge/game-phrases.json`), unless a token, a reported name or the death recap supplied it. Item names are not used (many are ordinary English), junk rows (test, unused, deprecated) are skipped, and the index is rebuilt per data build and table hash and never built from a damaged table. The refusal names the source of each run. A real area name that reads as plain English, such as "gold mine", stays refused. Without complete synced data only the built-in list applies, and the order reply or the roast log says why. Not closed: the synced data has no spell or NPC names, so an ability or NPC phrase missing from the built-in list still gets through.
- The roast TL;DR line on the stream card goes through the same word and phrase checks, with no tokens: NFKC; only `A-Z a-z 0-9`, space, `, . ' ’ ‘ - : ! ? % ( ) " ;` (any brace drops the line); and every word (any case) a number, a recap word or a plain word from `bridge/order-words.json` or the new `bridge/roast-words.json` (about 3,600 everyday English words and their verb forms, without race, class, ability, title, place or creature-family words). A lowercase name or one split by a zero-width character no longer gets through, and a dropped line is logged with the reason. A typed line that does not start with `Death recap:` makes no card; one that does is treated as a recap. The `order_issue` description and the roast instructions say how. See docs/LIVE-SESSION.md and docs/CONFIGURATION.md.
- The in-game Orders card (`addon/ClaudeWoW/Orders.lua`): the current order, its progress bar and up to 3 goal bars, under the quest tracker in the objective tracker's own header, fonts and progress bars (each template and atlas probed, with a plain fallback). The bridge sends it as a `goals` field in the slot files and `Inbox.lua` (at most 640 bytes; order text and goal titles checked by the order validator again; a token order shows the expanded names stored in its refs). It uses no slot load of its own: the card changes on the next slot the addon reads anyway, and a goal write republishes the slot files at once. The field carries the character key; the bridge leaves it out only when the context names no character, and sends an empty field (the card hides) when the store cannot be read. No order hides the card, and so do an order for another character, an `Inbox.lua` written more than 5 minutes before a login or `/reload` reads it (a slot file that old is ignored, so a stopped bridge cannot bring an order back), a pet battle and a vehicle UI. A slot file without the field (an older bridge) changes nothing. A drawing error hides the card, is said once, and never stops the rest of the slot read. `/claude orders on|off`, `/claude config orders` and a gear-menu checkbox show or hide it; the header button collapses it. See docs/LIVE-SESSION.md.
- Game state telemetry, Phase 1 (`Telemetry.lua`, `bridge/telemetry.js`, `bridge/events.js`). The addon sends quiet `kind=gs` records with money, level and XP, zone uiMapID, profession ranks, watched item counts and free bag slots, equipped item IDs, watched factions, deaths and learned recipes: IDs and numbers only, each section with a hash, the record with its own clock-based sequence and the character it belongs to, keyed as `goals.json` is (first name and realm, e.g. `Bone-Forever`; two characters sharing a first name on one realm share a folder). Deaths and recipes are kept per character, at most 20. Forever APIs only (`C_SkillInfo`, `C_Item.GetItemCount`, `C_Container.GetContainerNumFreeSlots`, `GetInventoryItemID`, `C_Reputation.GetFactionDataByID`/`GetWatchedFactionData`, `C_Map.GetBestMapForUnit`, `NEW_RECIPE_LEARNED`), and a `cap` section names any the client lacks, which the bridge logs. Records never use the message id space (`submit()` branches on `kind=gs` before any dedupe, ack, sig or `lastId`), are never retried, never set `pixelFailed` and honour the paused-shots rule; they count as sent only when their shot succeeds, ride on screenshots the addon takes anyway in the room messages leave (never on a message retry), collect only after a change event, plus a shot of their own at most every 2 minutes (never while an edit box has the keyboard) or right after a level up, death or new recipe; at most one every 30 s and 120 an hour, 1.5 KB each. The addon sends nothing until the bridge advertises the new `gs` slot field (also read from `Inbox.lua` at login), which carries the hashes it holds for up to 4 characters (a mismatch makes the addon resend that section) and the watch list (`telemetry.watch` in `config.json`). The bridge alone writes `goals/<Name-Realm>/snapshot.json` and `events.jsonl` (rotated at 5 MB, 2 files kept). New `claude-wow events [--follow] [--min N]` prints one JSON line per event, merges 10 s bursts and prints at most 40 bursts an hour; a watched item reaching its target is a `goal_complete` event, once per target (a snapshot from before this may fire one repeat). Keys the bridge refuses are listed in the slot field, and an addon whose key is listed stops sending. New `/claude config telemetry on|off` and a **Send game state to Claude** gear-menu checkbox (`ClaudeWoWDB.settings.telemetry`). A telemetry-only screenshot comes at most once every 2 minutes and shows the client's usual "screen captured" text, as message shots already do. A malformed `snapshot.json` is cleaned up, never a crash. New `ClaudeWoWDB.telemetry` keys (`seq`, and per character in `chars`: `deaths`, `lastDeath`, the last 8 `learned`, `seen`); a new addon file, so restart the client once.

- Goals and orders, Phase 0 (`bridge/goals.js`). A live Claude Code session gets `goal_set`, `goal_list` and `order_issue` from the channel server; each call goes over the bridge socket, and the bridge alone writes `<CLAUDE_WOW_HOME>/goals/<Name-Realm>/goals.json` (atomic rename). One goal type: a profession rank, at most 8, progress read from the game context. One current order plus the last 20. The order text is an allowlist: NFKC-normalized, only `A-Z a-z 0-9`, space and `, . ' - : ! ? %`, and every word (any case) must be a number, the character, a reported profession or a plain word from `bridge/order-words.json`, so no zone, NPC, item or quest name, slash command or macro gets through. An order needs a game context confirmed in the last 15 minutes. Each change is pushed to the stream overlay as `{"action":"orders",...}` on `plugins.stream.url`, with `asOf` from the context (never the current time). In-game Claude runs get `--disallowedTools` for the two write tools, `Read` of `live.token` and `Edit` of `goals/`; a Need roll can never grant, keep or offer the goal tools. The bridge refuses a goal call whose channel pid is not a child of its Claude Code pid or runs under an agent run. Shell access granted to an in-game run can still reach both files. See docs/LIVE-SESSION.md.

### Removed

- NPC sightings. The addon no longer records NPC or flight-master spots (`ClaudeWoWNpcDB`) or adds an "NPCs seen on this map" line to the situation block, and the agent no longer gets `CLAUDE_WOW_SAVED_VARIABLES`. The saved table drops out of the SavedVariables file at the next logout.

### Fixed

- The "≈$ API" cost for Claude Opus 5.5 used Opus 5 rates ($5 in, $25 out) and overstated every Opus 5.5 run by 25% or more (cache reads by 2.5x). It now uses the list price ($4 in, $20 out, $0.20 cache read), checked on 2026-09-30 against https://platform.claude.com/docs/en/about-claude/pricing. Claude Opus 4.5 and Sonnet 4.5 runs now show a cost too.
- The game context's `Talents:` line shows on WoW Forever again. Forever has no `GetNumTalentTabs`/`GetTalentTabInfo`, so the line never appeared. The addon now reads the active talent loadout the way Blizzard's own Forever talent frame does (`C_SpecializationInfo.GetCombatConfigIDForSpecGroup`, then `C_Traits.GetConfigInfo`, `GetGroupDisplayInfoByTreeID` and `GetGroupCurrencyInfo`): each tree's name and points spent, in the client's order. It falls back to the old talent-tab functions on clients that have them. No loadout for the active spec group, no spent data yet, or no talent API: no line. A talent read error never stops the context. The addon primer no longer tells agents to use talent tabs or other Classic functions that Forever lacks; it gives the trait-tree chain instead.
- No more 16-chat limit. The fallback chat list pages 16 at a time and opens on the active chat's page. A fresh-install restore still brings back the 16 newest chats.
- Live sessions: a Claude Code session opened in this repo without the channel flag no longer shows up as live and swallows messages. The bridge reads the session's command line and marks it `listening` only with `--dangerously-load-development-channels server:claude-wow` (or `--channels` naming it); picking one that is not listening prints its exact `claude --resume <id> --dangerously-load-development-channels server:claude-wow` restart command and a `[resume headless]` link. A message that shows no sign of pickup in 45 s (`plugins.live.pickupMs`) fails with one line instead of "working..." forever, and a late reply still lands in the chat.
- `/claude -r` is a short list of clickable rows instead of a wall of text: number, title (Claude Code title or first prompt), folder and git branch, age, and a `live` / `running, not listening` / `resume` badge. Live sessions first, no duplicates, 8 rows and a `[more]` link, `(this chat)` on the current one; links in the whisper tab, buttons in the workspace.
- The channel server stays idle when its Claude Code process is not listening (no channel flag, or a `-p`/`--print` run): no tools, no channel capability, no instructions, no bridge connection. Registering it at user scope no longer costs context in every session. `/claude -r` never lists a `-p`/`--print` process.

- No more "ClaudeWoW has been blocked from an action only available to the Blizzard UI" at every login and `/reload`. The death roast registered `COMBAT_LOG_EVENT_UNFILTERED`, which this client restricts to the Blizzard UI. The roast now reads the game's death recap (`C_DeathRecap`, the same data as the **Death Recap** button) and falls back to the player's `UNIT_COMBAT` hits (amount, school, crit, no attacker name) plus the target and mouseover at death. It registers `PLAYER_DEAD` and `UNIT_COMBAT` only while it is on. Recap cap (900 bytes) and cooldown (2 minutes) are unchanged.
- Live UI widgets can no longer trigger the same popup: the bridge refuses a widget that names `CombatLogGetCurrentEventInfo` or a restricted event (`COMBAT_LOG_EVENT_UNFILTERED`, `COMBAT_LOG_EVENT`, `MINIMAP_PING`, `UNIT_PING_PIN_ADDED`, ...), the widget sandbox refuses to register them, and the system-prompt hint points to `UNIT_COMBAT` instead of the combat log.

### Added

- Roast Cam: when a death roast is written, the bridge also POSTs `{"action":"roast","roast":{...}}` to the stream service's `/control` (the `plugins.stream.url` and `plugins.stream.enabled` settings, no new config). The card text is the roast's TL;DR line without `[bridge]` notes, and it is left out when it has a capitalized word that is neither in the recap nor a plain English word, or a `|` escape code; the roast instructions also tell the model to name only what the recap names. `killer`, `ability`, `overkill` and `zone` come only from the addon's death recap and are left out when the recap does not have them: no attacker for `UNIT_COMBAT` hits, "something unseen", "the environment" or "The environment", a killing blow the recap summary does not confirm, or "somewhere unmapped". Only a run that finished `done` is sent, so an error, a cancel or a timeout followed by a retry counts one death. Talking back in the Death roasts chat sends nothing, and neither does a bridge run with `--inject` or `--once`, which exits before a POST could finish. A down service is only logged. Plugins get an optional `finished(job, outcome, core)` hook for this.
- `claude-wow data sync`: caches the Forever client tables from wago.tools (product `wow_cn_beta`) in `~/.claude-wow/data/forever/<build>/` as JSON Lines plus a `manifest.json` (source, URLs, build, build family, per-table SHA-256, rows kept and dropped by reason). Items, quest IDs, zones, flight paths with uiMap percent positions, UiMap tables, and the optional profession abilities and spell reagents. Every row is checked on the way in; the swap is atomic with a `current` pointer that never names a missing folder, and a lock file that two syncs cannot both take over. It follows the newest `1.60.1` build and switches families only with `--build`. Nothing runs it on its own yet, and the data is never committed or shipped. See [docs/CONFIGURATION.md](docs/CONFIGURATION.md#game-data).
- `wowdata`, a read-only MCP server over that data (`claude-wow data-mcp`), wired into Claude `ask` runs by the bridge. Five tools: `wow_item` (by ID or name, with the quest it starts; by ID also the recipes that use it), `wow_quest` (an ID check and the items that start it; the client tables have no quest titles, so it never returns one), `wow_flights` (by ID, name or uiMapID, with map positions), `wow_where` (maps, areas and flight paths by name, or one map's parents and children) and `wow_sources` (provenance and what the data does not hold). Every answer is JSON with `source`, `build` and `trust`, and `buildCheck` says whether the data is in the client's build family; rows for another family or an unknown client build are not labeled plain `client-data`, and a missing or damaged table is reported as unavailable instead of as "not in the data". The bridge passes `--mcp-config` with its own absolute command and `alwaysLoad`, and adds `mcp__wowdata` as a run-only rule, so `config.json` is untouched; a denied tool under an allowed `mcp__<server>` rule is never offered for Allow (and so never saved). With no synced data, ask runs go without it and the bridge logs that once. When Claude reports an MCP server as not connected, the bridge logs it, and a failed `wowdata` is named in the reply. The sync now also caches `SkillLine` (profession and skill names). A new `bridge/gamerefs.js` expands `{item:ID}`, `{map:ID,x,y}` and `{skill:ID}` to canonical names and rejects unknown IDs; replies do not use it yet. See [docs/CONFIGURATION.md](docs/CONFIGURATION.md#the-wowdata-server).
- `node dev/measure-ask.js` runs 10 fixed game-chat prompts through the real `claude` CLI on two models, with the same system prompt, situation block and tool rules as an in-game `ask` run. Each model runs in one stable folder, and each prompt gets a resumed follow-up turn, so cold first turns, first turns of a new chat and resumed turns are priced separately. It records cost, latency, answers, the `claude` version and argv, and stops before a run would pass the budget (`--budget`, default $3). Results for Opus 5.5 vs Sonnet 5.5 are in `docs/plans/measurements/step1-ask-model.md`.
- The workspace window's black bar shows the chat's title across its full width instead of the folder / agent / plugin breadcrumb. Hover it for the folder, agent and plugin; click to rename; right-click for the chat menu.
- New chats are named by a lightweight model. The first message asks the bridge for a title, which runs `claude-haiku-4-5` (config `titleModel`, `false` to turn it off) with no tools and no saved session next to the agent run. Until it lands the chat shows its first words; a title that misses the reply arrives with the next one; a name you chose is never replaced.
- Stream control from the game (`Stream.lua`, `stream` plugin): `/stream starting|raid|game|code|brb` switches the scene, `/stream quest <text>` shows a quest line by hand (and turns follow off), `/stream quest auto` and `/stream follow on|off` hand the quest line back to the game, and `/stream pane left|right|full` moves the game pane. With follow on (the default), the addon sends the super-tracked quest (or the first watched one) with up to 5 objectives, plus the title of the chat open in the addon, whenever either changes: identical states are dropped, and at most one update goes out every 8 s, with the latest state sent when the window ends. Every send is a small JSON object on a quiet "Stream control" chat bound to the new `stream` plugin, which POSTs it to `plugins.stream.url` (default `http://127.0.0.1:4466`) `/control` with a 3 s timeout and never starts an agent. Commands print the service's one-line answer, track updates print nothing, and a service that is down answers "Stream service is not running". Quiet chats keep their sends and replies out of the chat history, the whisper tabs and the game chat. New `ClaudeWoWDB.stream` keys `follow` and `chat`; a new addon file, so restart the client once.
- Whisper-first UI: whisper tabs are on by default and a chat's tab is where you talk to it. The active chat's tab opens at login once the bridge names its agent; a reply shows whole when short and as its TL;DR with a `[full reply]` link when long; progress is one line updated in place (`Claude is working... 45s · 12 actions - Editing Map.lua  [cancel]`); denied commands get `[Need] [Greed] [Pass]` links, macros a `[Create macro: Name]` link that opens the Create-macro prompt, map routes a `[show route]` link that opens the map; the bridge status is one line with a `[connect]` link; `/claude` commands typed in a tab answer there. An install that had turned the tabs off by hand keeps them off; one that never touched the setting moves to on once and is told so in the tab.
- The workspace window (`Window.lua`): opens only on demand (bare `/claude` in the game chat, the new **Claude WoW: open or close the workspace** key binding, the compact bar, a `[full reply]` link). While open it steps aside for bags, the character sheet, the spellbook, vendors, the bank, mail and other Blizzard panels and goes home when they close, steps away while the maximized map or the game menu is up, dims to 35% while you move or fight and is opaque under the mouse, remembers its size and place per character, snaps to the screen edges and follows the UI scale. It uses the Dragonflight metal frame where the client has it.
- `/claude config ui whisper on|off`, `dim <10-100>|off`, `dodge on|off`, `autohide on|off`, `reset`; `ui list|remove|run` still manage live widgets.
- `/r` replies to the chat that answered last again, with no hook on the chat edit box. When a reply lands the addon puts `<Agent> [<chat>]` first in the game's own last-whisper list (`ChatFrameUtil.SetLastTellTarget`), so the game's `/r` and reply key open a whisper to it with the game's own `To Claude [chat]:` header, and the pre-send callback hands the line to that chat (the one that replied last when two share a name) with whisper tabs on or off. A real player's whisper puts them first again, so `/r` answers whoever messaged last. The name has a space and brackets, so no player can have it; the leak filter, now installed at login whatever the setting, reports one that reaches the server. `/claude diag` names the current `/r` target. `/cast`, `/gquit` and `/r` to players are unaffected; `tests/wow_stub.lua` models the taint of the last-whisper list and the edit box's attributes to prove it.

- Live session (`live` plugin): a chat bound to it (`/claude-wow plugin live`) talks to a Claude Code session already open in a terminal instead of starting `claude -p`. The session is started with `claude --dangerously-load-development-channels server:claude-wow` (or `--resume <id>` plus the flag) from this repo, whose new `.mcp.json` registers `bridge/channel.js`, a hand-written MCP channel server (no npm dependency; `claude-wow channel` in the binary). The bridge forwards each message, with the game context, over a Unix socket (`live.sock` in the home folder, `0600`; a named pipe on Windows) guarded by a per-start token both sides prove; the session answers with the `wow_reply` tool, and the answer takes the normal reply path (window, whisper tab, echo with the `TL;DR:` summary, voice). Tool approvals the session needs come up as the Need/Greed roll (Need or Greed allow, Pass denies; unanswered ones are denied after 2 minutes). With no session connected the chat says so and prints the start command; `/claude-wow live` lists the sessions. New `plugins.live` keys. See [docs/LIVE-SESSION.md](docs/LIVE-SESSION.md).
- Achievement toasts: dev milestones pop a gold achievement-style banner in game with an icon, a title, points and the achievement sound. The bridge reads the agent's shell commands and their results (Claude Code and Codex) and awards a finished task, tests passing after failing, a git commit, a push, and a few jokes (Merged on a Friday, Night Owl, It Works On My Machine, Rubber Duck, Leeroy Jenkins). One-time awards are kept in `state.json` and ride to the game in the slot files. `/claude-wow achievements` lists them; `on|off` turns the toasts on or off; `"achievements": false` in the config turns the detection off.
- Live UI widgets: ask the agent for a small display element (a DPS meter, a buff timer bar) and its Lua loads in the game at once, without `/reload`. The agent writes a ```` ```wowui <name> ```` block or appends to `CLAUDE_WOW_UI_FILE`; the bridge refuses sources that name protected or outward actions, keeps the widgets versioned in `state.json` and ships them in the slot files like map layers. A new `ui` plugin surface (on `ask` and `claude-code`) gates the system-prompt hint and the file. The new `Widgets.lua` runs each widget in a sandboxed environment inside a `pcall`, reports errors to the chat window, and restarts saved widgets at login. `/claude-wow ui` lists them; `remove <name>` and `run <name>` control them. New saved variable `ClaudeWoWWidgetDB`; a new addon file, so restart the client once. See [docs/UI-WIDGETS.md](docs/UI-WIDGETS.md).
- Linux support: the game under Wine on an X11 session. `bridge/capture_x11.py` (python3 + libX11 through ctypes, no packages) does what `capture.ps1` does, finding the game window by its Wine WM_CLASS (`wowb.exe`) and tolerating a few pixels of misalignment. `npm run probe` saves what the capture sees to `bridge/probe.png`. New `capture` keys: `python`, `windowName`, `keepComposited`. `setup.js` looks for the client inside Wine prefixes. See [docs/INSTALL-LINUX.md](docs/INSTALL-LINUX.md).
- Map layers drawn by the agent: numbered route pins joined by lines, quest stops and marks on the world map (zone and continent views), plus a navigator with an arrow and the distance in yards to the next stop that advances as you arrive. The agent's tools append commands to the file in `CLAUDE_WOW_MAP_FILE` (set per run), or the agent ends its reply with a ```` ```wowmap ```` block; the system prompt explains both. The bridge validates them, keeps the layers versioned in `state.json` and ships the whole set in the slot files, so nothing is applied twice and a client that lost its saved data gets them back on its next hello. See [docs/MAP.md](docs/MAP.md).
- Herb and ore spawns on the world map from an optional `ClaudeWoW_Nodes` data addon, filtered by your gathering skill. `/claude-wow map` (or `/aimap`) toggles them (`ore`, `herb`, `filter all|skill`) and controls layers and navigation (`show`, `hide`, `nav`, `next`, `prev`, `stop`).
- The game context includes the quest log (quest ids, `*` when ready to turn in); its cap goes from 700 to 900 bytes.
- Ready-made macros: when you ask for a macro, the agent writes it in a ```` ```wowmacro <Name> ```` block and the reply gets a **Create macro** button (or **Update macro** when one with that name exists). A click saves it as an account or character macro and puts it on your cursor to drop on an action bar. It asks before replacing a different macro of yours or saving one that runs code (`/run`, `/script`, `/click`); `/claude-wow macro undo` reverts the last one. The bridge validates the blocks (name up to 16 characters, body up to 255 bytes, 6 per reply), sends them as `macros` on the reply record and keeps a readable copy in the text; blocks after the `TL;DR:` never reach the game-chat summary. Nothing is saved in combat, and the addon never runs a macro.
- macOS support for a native client: `bridge/capture_mac.py` (python3 stdlib only) finds the game window through System Events and grabs its top-left corner in-process through CoreGraphics (ctypes, about 20 ms a frame; it captures only the strip's 808x272 points and falls back to the `screencapture` binary writing a raw BMP when CoreGraphics cannot load or Screen Recording is denied - `--backend screencapture` forces that); the bridge starts it on macOS, and `setup.js` recognises a `.app` client under `/Applications/World of Warcraft` and sets `capture.processName` from the bundle. `npm run probe:mac` saves what the capture sees. Contributed and tested live by its author; the decoder is covered by the codec round-trip test.
- Screenshot transport (`capture.mode: "screenshot"` in `config.json`): instead of screen-capturing the strip four times a second, the addon calls `Screenshot()` with the strip up for two frames and the bridge decodes the PNG/TGA the client writes to its `Screenshots` folder (`bridge/decode.js`, zero dependencies, same cell/magic/checksum rules as the capture scripts; `bridge/screenshots.js` watches the folder) and deletes it. The bridge names its transport in every slot file, the addon remembers it, sets `screenshotFormat` to `png` while the mode is on and restores the player's value when it ends or at logout. Your own screenshots, and files from before the bridge started, are never touched. `pixel` stays the default. On this transport the strip is drawn dark (`capture.screenshotLevels`, default 0/60 of 255, shipped to the addon in the slot files) since a screenshot is bit-exact, so it is all but invisible for the two frames it is up; the pixel transport keeps its full primaries and 128 threshold.
- **Antigravity** (`agy`, Google's Antigravity CLI) and **Hermes Agent** (`hermes`) next to Claude Code, Codex and Grok: `/claude-wow agent agy` or `hermes`, with their own blocks under `agents` in `config.json`. Hermes prints plain text, so the bridge reads its reply when the process ends (no live progress) and never passes it `--yolo`, even from `extraArgs`. Contributed with captured streams in `tests/agents_test.js` and a live check by their author on Windows. `CODEX_BIN` names the Codex launcher when the one on `PATH` isn't the right one.
- Whisper tabs (`/claude-wow whisper on`, off by default): each chat becomes a native whisper tab in the chat dock, opened with its first message (`FCF_OpenTemporaryWindow`) and named after the chat. Replies are written into it as incoming whispers in the whisper colour and flash the tab like a player's whisper (`FCF_StartAlertFlash`, else the tab glow by hand); what you send shows as `To Claude:` with a system-coloured working line and the bridge's progress under it. Enter in that tab, or `/w Claude ...` in any chat box, goes to the agent: the `ChatFrame.OnEditBoxPreSendText` callback empties the box after the game parsed its slash commands and before it sends (see Fixed), and should a whisper still get out, the server's "No player named" answer is rewritten into a red LEAK line and counted (`/aiwhisper status`). Rename retitles the tab, delete closes it, `off` closes them all.
- Plugins ([docs/PLATFORM.md](docs/PLATFORM.md)): the bridge is a core (transport, chats, sessions, transcripts, restore, the window, whisper tabs, the game-chat echo, map layers, macros, game context) plus plugins that decide what a message does. `bridge/plugins.js` is the registry and routing (an address at the start of the text such as `@ask …`, else the chat's binding, else a plugin's `match()`, else the default); each plugin declares `id`, `label`, `aliases`, `match`, `tools` (its own lines in the system prompt), `surfaces` (`map`, `macro`) and `handle(job, core)`. Two ship: **`ask`**, the default, general in-game chat (game questions, quest research, map routes, macros) with no project or folder, run in a scratch folder of its own (`plugins.ask.cwd`); and **`claude-code`**, an agent session in a folder, exactly what the bridge was. A chat carries its binding as a `plugin=` flag (and `plugin` in the reload outbox); chats from before plugins are bound to `claude-code` once by the addon, a new chat inherits the binding of the chat it was made from, and a chat that changes plugin starts a fresh session. `plugins.default` in `config.json` sets the default, `--plugin` picks one for `--inject`, and `npm run test:live` now tries both. In game, `/claude-wow plugin [ask|claude-code|default]` binds the current chat and the chat's right-click menu gains **Plugin...**, mirroring `/claude-wow agent` and **Agent...**; the window footer and `/claude-wow diag` show the binding.
- Vision (`/claude-wow vision on`, off by default; `/claude-wow look <question>` for one message): on the screenshot transport the bridge keeps the rest of the screenshot it decodes the strip from, crops the strip's rows off, scales it to `vision.maxWidth` (1280) pixels wide (`bridge/vision.js`, zero dependencies) and attaches it to the agent's message as an image, with a system-prompt paragraph saying so, so "what is this item?" or "why is this boss killing me?" are answered from the screen. Claude Code takes the picture inline as an `image` content block in a stream-json user message (`--input-format stream-json`); Codex (`-i`), Hermes (`--image`) and Grok (a path in the prompt) get the PNG from `~/.claude-wow/tmp`, where it is deleted after the run and never more than `vision.keep` (6) pile up. The window footer and `/claude-wow diag` show the state; `node bridge/bridge.js --inject "..." --image <png|tga>` tries it without the game. Off, every run is exactly what it was.

- `claude-wow service install|uninstall|start|stop|restart|status|logs`: the bridge as a per-user background service that starts at login and comes back after a crash. macOS: a LaunchAgent (`~/Library/LaunchAgents/io.claudewow.bridge.plist`, `RunAtLoad` + `KeepAlive`); Linux: a systemd `--user` unit; Windows: a hidden launcher in the Startup folder. The bridge's output goes to a log under `~/Library/Logs/claude-wow`, `~/.local/state/claude-wow` or `%LocalAppData%\claude-wow\logs`, rotated at 5 MB with five files kept, and `~/.claude-wow/bridge.log` is rotated the same way instead of growing forever. `status` reports the pid, uptime and the last log lines. `claude-wow setup` runs `setup.js`. See [docs/INSTALL.md](docs/INSTALL.md).
- One-line installers: `curl -fsSL .../install.sh | sh` (macOS, Linux) and `irm .../install.ps1 | iex` (Windows). They check for Node 22.2+, fetch the code into `~/.claude-wow/app` (git or archive), put a `claude-wow` command on the PATH, run setup and offer the service; safe to re-run, never sudo, and every failure says what to do. A Homebrew tap layout (`homebrew/`) installs the bridge and command on macOS, with `claude-wow setup` doing the game side and a documented caveat about upgrades.
- The bridge as one self-contained binary per platform (`npm run build`; `build.js` runs `bun build --compile` for macOS arm64 and x64, Linux x64 and Windows x64, 60 to 85 MB each with `SHA256SUMS` alongside, and CI builds all four on every push): the bridge, `claude-wow setup` and `claude-wow service` with [Bun](https://bun.sh)'s runtime inside, so the machine that runs it needs neither Node nor a checkout. The capture scripts, the addon, `config.example.json` and the primer travel inside it and are written out under `~/.claude-wow/assets` on first use (`bridge/assets.js`), rewritten whenever a new binary carries a different copy; config, state and logs are found through `CLAUDE_WOW_HOME` exactly as before. `bridge/runtime.js` is the one place that knows whether the bridge runs on Node, on Bun or from the binary: the supervisor gains `claude-wow bridge [...]` (bridge.js in this process, no restarts), `claude-wow install-slots` and `claude-wow --version`, which is how the binary runs its own scripts, and a JavaScript launcher an agent CLI ships (npm's `codex.js`) is run with the node on the `PATH` when the bridge is the binary. The bridge keeps running on Node 22.2+ and now also on Bun from a checkout: `npm run test:bun` runs the same suite under `bun test`, and CI runs both on Windows, Linux and macOS. Daemon start, measured on an Apple Silicon Mac as the wall time of `--once` (supervisor plus bridge: modules, config, banner, one poll, exit; 15 runs, warm cache): 54 ms median with `node bridge/supervisor.js`, 24 ms with the binary; a bare process start (`service help`) 25 ms against 8 ms. Tens of milliseconds either way: the binary is about the install, not the start.

- Context growth in game. Every message resumes the chat's agent session, so its context only grows and each reply costs more than the last (measured: 107k tokens after 8 turns, 312k after 213). The bridge reads Claude Code's `usage` (the last assistant message's input + cache read + cache creation is what the next message carries; the result's per-model `modelUsage` prices the run at the API list rates in `CLAUDE_RATES`, `bridge/agents.js`, cache reads and writes apart, checked against Claude Code's own `total_cost_usd`), keeps it per chat in `state.json` (`sessionUsage`, with the turn count and when the session started) and ships it on the reply record (`ctx`, `turns`, `window`, `since`, `cost`) and in the restore bundle. The window's footer shows it like Claude Code's status line, `11m 58s · ↓ 106.9k tokens · ≈$2.41 API` (elapsed since the session started, the context, the session at list prices - a comparison, a subscription is not billed per token; a model with no listed rate shows tokens only), `/claude-wow context` prints it with the turns and the threshold, `/claude-wow diag` lists it per chat. Past `/claude-wow context <n>` (100k by default, `0` = off, persisted) the chat says so once per crossing, what ignoring it costs and what a fresh start loses, with a **New chat** button that does what bare `/claude` does; the warning also reaches the whisper tab or the game chat, wherever the reply went. Other agents report no context size: their chats show elapsed time and turns.

- Need / Greed / Pass on permissions: when Claude or Grok is denied a command, the addon pops a frame in the style of the group loot roll (`addon/ClaudeWoW/LootRoll.lua`, built from the `LootToast` texture, the `lootroll-toast-icon-*` atlases and the Skills-Bar timer that Blizzard's own `GroupLootFrame` uses). The denied command is the item, in epic purple, with a scroll icon for a shell command and a gear for any other tool; the icon tooltip lists the exact rules. **Need** is the Allow & retry path (the rules go into `allowedTools` for good). **Greed** allows them for the retry only: the addon sends a new `once=` flag (`allowOnce` in the reload outbox), and the bridge adds those rules to that one run's allowlist without saving them (`protocol.withRunOnlyRules`). **Pass** sends nothing and closes the denial. A 60-second bar counts down and runs out as Pass. The sounds are the client's own, by SOUNDKIT: `UI_EPICLOOT_TOAST` when it shows, then `UI_NEED_ROLL_POSITIVE`, `LOOT_WINDOW_COIN_SOUND` or `UI_NEED_ROLL_NEGATIVE` for the choice. Several denials queue. `/claude-wow roll off` brings back the Allow & retry button. A bridge from before `once=` ignores the flag, so Greed against an old bridge retries without the rule.

### Changed

- Every link the addon writes is now an `addon:claudewow:...` link, which the client's own AddOn link handler takes, so a click no longer falls through to the item tooltip. Older `claudewow:` links in the chat log still work.
- The mini bar is smaller (200 x 26) and says what a click does; a fresh install shows it by default with the status light.
- Messages sent from a tab no longer mark the window as open for the next login, and a reply shown in a tab no longer counts as unread on the bar.
- **The in-game commands mirror the `claude` CLI.** `/claude <text>` starts a new chat (`claude "<text>"`), `/claude -c [text]` continues the current one (`--continue`), `/claude -r <id|name|n> [text]` resumes a session (`--resume`) and bare `/claude -r` lists the running and recent sessions with id, name, folder and age, clickable in the game chat (the `/resume` picker). `-r` chooses for you: a Claude Code session running with the claude-wow channel gets the chat live, any other one (one of your chats, or a Claude Code session from `~/.claude`'s history, looked up by the bridge when the list does not have it) is resumed headless with `claude -p --resume <id>` in its own folder; an id prefix two sessions share is answered with both. `--model`, `--effort`, `--permission-mode`, `--add-dir` and `--agent` (which CLI) are per-chat settings, combined with text on a new chat (`/claude --model opus fix the build`) or with `-c` on the current one; `-n` names the chat. `--flag=value`, quoted values, `-` to clear and a bare flag to show all work, and a message that only starts with something flag-like is a message. The bridge passes them to each agent in its own spelling (Claude `--model`/`--effort`/`--permission-mode`/`--add-dir`; Codex `-m`, `-c model_reasoning_effort=`, the sandbox, `--add-dir`; Grok `-m`; Antigravity `--model`, `--mode`, `--add-dir`; Hermes `-m`) and ends the reply with a note naming any it had to leave out. New record flags `model=`, `effort=`, `pm=`, `dirs=`, `resume=`, `live=` (and `opts` in the reload outbox), a `sessions` list in the slot files, `claudeDir` and `claudeSessions` in `config.json`, `bridge/sessions.js`, and the channel server now tells the bridge which Claude Code process started it.
- **Settings moved under `/claude config <key> [value]`**: voice, roast, whisper, echo, vision, roll, achievements, ui, map, macro, context, signal, mode, longchat, auto, bind, diag and, as an advanced setting, plugin. `/claude config` alone lists them with their values. The client's own verbs stay as `/claude <verb>` (help, diag, cancel, copy, clear, rename, delete, cd, look, reset, hide, mini, reload, resend, slots) with the same rule as before: a verb followed by something it does not take is a message.
- **Plugins are chosen for you.** A chat with a folder (`/claude cd`) goes to `claude-code`, a chat attached with `-r` to a running session goes to `live`, any other to the bridge's default (`ask`); nobody has to type a plugin name.
- **`/claude <text>` always starts a new chat** and sends the text there, like opening a new terminal. A command word that fits its command still runs it (`/claude diag`, `/claude agent codex`); `/claude-wow <text>` and typing in a whisper tab continue the current chat. At the chat limit (16) nothing is lost: the game chat says so and the text waits in the window's input box. A slash command typed in a whisper tab now applies to that tab's chat.
- **The strip is eight times denser on the screenshot transport** (codec 2, `capture.screenshotCodec`, default `2`): 2 px cells instead of 4, four levels per channel instead of two (six bits a cell instead of three), 400 cells a row, so the same message takes an eighth of the screen area. A typical message (a few hundred bytes with its record fields) is one 800×2 px near-black line for the two frames it is up; a 1 KB message is four rows, 8 px tall, where it was fourteen rows, 56 px. The levels are spread evenly between `capture.screenshotLevels`' `off` and `on` (0/20/40/60 by default, `Codec.DenseLevels`), and four ramp cells lead every strip with each channel at level 0, 1, 2, 3, off which `bridge/decode.js` reads the levels this frame really holds and classes every sample by the nearest (`denseReader`), so the numbers are the drawer's business and a ramp that does not rise is not a strip; a bit-exact screenshot puts every sample exactly on a level, so with the defaults the ramp is insurance and a self-check rather than a need. The strip format is versioned by its magic: codec 2 is `C7 2A`, codec 1 stays `C7 1A`, the slot file says which one the bridge wants (`strip = { on, off, codec }`), the bridge decodes both at every offset, an addon from before the field draws codec 1, a bridge from before it never asks for codec 2. The pixel transport, and its capture scripts, are untouched: codec 1, 4 px cells, full primaries, the `>= 128` threshold. `tests/codec_test.js` round-trips the real `Codec.lua` through the Python decoders for codec 1 and through `decode.js` for codec 2 (default levels and two other level sets), `tests/decode_test.js` covers the ramp, the margins, the cross-codec cases and the error verdicts, and `tests/addon_test.js` draws both from the addon and reads them with the bridge decoder. Not yet verified in the game: that the client renders 2 px textures on exact pixel boundaries; `capture.screenshotCodec: 1` is the way back if it does not.
- **The screenshot transport is the default.** A new install, and any `config.json` without a `capture.mode`, starts on it (`protocol.chooseTransport`); an existing config with an explicit `mode` keeps what it has. It is verified end to end on macOS and needs no screen capture, no Screen Recording or Automation permission, no window discovery and no python, so `setup.js` now reports python3 (and, on macOS, the two permissions, whose check it skips) as the deprecated pixel fallback's business only, and `claude-wow service install` phrases its macOS note the same way.
- **Automatic fallback to the pixel capture.** When the client cannot take the screenshot the transport needs, the addon says so on its records (`shot=missing`: no `Screenshot()` function; `shot=failed`: `SCREENSHOT_FAILED` on every try; on the strip's flags and in the reload outbox, which is how it reaches a bridge that is not watching the screen) and tells the player once. The bridge switches to the pixel capture at once (`fallbackToPixel`), logs `TRANSPORT FALLBACK: ...` with the reason and what the fallback needs, remembers it as `transportFallback` in `state.json` so the next start goes straight to pixels (the banner says why), and ships the reason as `transportNote` in every slot file, which `/claude-wow diag` shows. An explicit `capture.mode` always wins over the memory. Covered by `tests/transport_test.js` (the bridge against a fake home and agent), `tests/addon_test.js` and `tests/setup_test.js`.


- **Renamed to claude-wow** (from wow-ai; the project was wow-claude before that). The addon is `ClaudeWoW` (saved data `ClaudeWoWDB` and `ClaudeWoWMapDB` in `ClaudeWoW.lua`, slot addons `ClaudeWoW_S###`, signal files under `Interface\AddOns\ClaudeWoW`, the optional node data addon `ClaudeWoW_Nodes`), the slash command is `/claude` or `/claude-wow` and nothing else (`/wow-ai`, `/ai`, `/ask`, `/wowai` and `/wow-claude` are gone, not aliased; `/r`, `/aimap` and `/aiwhisper` stay), the command is `claude-wow` (no `wow-ai` alias), the service `io.claudewow.bridge` / `claude-wow-bridge` / *Claude WoW bridge.vbs*, the environment variables `CLAUDE_WOW_PROJECT`, `CLAUDE_WOW_MAP_FILE`, `CLAUDE_WOW_MAC_BACKEND` and `CLAUDE_WOW_SERVICE` (`WOW_AI_PROJECT` and `WOWAI_MAC_BACKEND` are still read), the installer's folder `~/.claude-wow/app`, the Homebrew formula and tap `claude-wow`, the repository `rdimascio/claude-wow`. `setup.js` migrates from either old name: the saved data is copied to `ClaudeWoW.lua` with the globals renamed (the old file is kept), the old addon and slot pool are removed, and an old `config.json` is rewritten; agent sessions are keyed by chat and carry on. `claude-wow service install` and `uninstall` remove the old name's service, and the installers carry `config.json`, `state.json` and `transcripts.json` over from `~/.wow-ai` and remove the old command. Re-do `/claude-wow bind <key>` if you had a hotkey.
- The installers and the Homebrew formula no longer need Node.js. `install.sh` and `install.ps1` fetch the binary for the machine from the GitHub release into `~/.local/bin` (Windows: `%LocalAppData%\Programs\claude-wow\bin`), verify it against the release's `SHA256SUMS`, run it once, and install from source instead, with the Node 22.2+ check as before, only where there is no binary for the platform, no release yet, or `--from-source` (`CLAUDE_WOW_SOURCE=1`) asks for it. `claude-wow service install` from the binary writes the binary alone into the LaunchAgent, the systemd unit or the Startup launcher, running from the home folder so `defaultCwd` applies as documented. The Homebrew formula's stable install is the binary for the Mac's architecture; `--HEAD` stays the checkout with Homebrew's node. A folder listing is not sorted under Bun (Node's is): setup's first account and first game executable, and the screenshot sweep's batches, are sorted now, so a checkout and the binary make the same choices.
- `CLAUDE_WOW_HOME`: the bridge keeps `config.json`, `state.json`, `transcripts.json`, `bridge.log`, `tmp/` and `mapjobs/` in a home folder instead of next to its code: `CLAUDE_WOW_HOME` when set, else `~/.claude-wow`, else (for a checkout that still has one) `bridge/`. `node setup.js` copies an existing `bridge/config.json`, `state.json` and `transcripts.json` to `~/.claude-wow` once and writes new configs there. The code can now be replaced without touching any of it, which makes the Homebrew formula a first-class route: the keg holds only code and `brew upgrade` keeps the config and the agents' sessions. The bridge's banner prints the folder it chose. See [docs/CONFIGURATION.md](docs/CONFIGURATION.md#where-the-bridge-keeps-its-files).

### Fixed

- Every Enter to open chat, every chat type change (`/s`, `/g`, Tab) and every Esc raised "attempt to call a nil value" at the game's `UpdateHeader()` calls on `ChatFrame1EditBox` (`ChatFrameUtil.lua:542`, `ChatFrameEditBox.lua:181`, `:206`, `:602` on 1.60.1.70124). The addon post-hooked the edit box's `UpdateHeader`, `ProcessChatType` and `ClearChat` with `hooksecurefunc` for `/r`, and on this client the wrapper it put in the `UpdateHeader` slot calls a nil. The addon now hooks no edit-box method at all; the pre-send callback on `EventRegistry` is its only chat seam. `/r` to the agent is back without any of these hooks, through the game's own reply (see Added).
- The status light went red 5 minutes after every reply because the game never saw a presence beat (`beats seen: 0`). The client only sees files that existed when it launched, and the bridge created a new presence file every 30 s; acks, readiness signals and heartbeats were invisible the same way. Every signal file now exists before the game starts and the bridge signals by deleting it: two presence rings of 2000 (`presence/a`, `presence/b`), and `ack`, `sig` and `act` for all 200 slots. The addon checks at every login that a deleted launch-time file reads as missing and uses the beats only then (otherwise the slower 12/22-minute windows); it reports the result on the next strip (`pt=`), along with whether a file created mid-session is visible (`lc=`). `/claude diag` shows the scheme and both results, and `npm run doctor` warns about signal files created after the running game started. Run setup and restart WoW after updating.
- A command that touches a path outside the chat's folder (`touch /tmp/x` from a chat in a project) rolled for `Bash(touch:*)` forever. Claude Code 2.1 blocks such a path whatever the allow rules say (`touch in '/tmp/x' needs approval. The path is outside the working directories for this session`), and only `--add-dir` opens it. The bridge now reads why each denial happened (the `system`/`permission_denied` event, else the tool's error result) and rolls for the folder instead, as `AddDir(<folder>)` (the nearest folder that exists, since Claude Code drops an `--add-dir` that does not): Need adds it to the chat's `--add-dir` list for good, Greed sends it with the retry only, and neither touches `allowedTools`. A retry that is denied again for a rule or folder it already has is not rolled again: the reply says why in one line. Need on a missing rule also reaches the very next run now; the rule used to be saved after that run's allowlist was built, so the first retry went without it.
- Battle.net marked the game not playable with "Permissions check failure (2113)" and its update failed. Blizzard installs every file and folder in the game tree as `0777`, and the bridge and installer wrote theirs with the default umask (`0644` files, `0755` folders); the presence `.wav` the bridge writes every 30 s meant a fresh `0644` file almost always sat under `Interface/AddOns/ClaudeWoW`. Every file and folder the bridge, `install-slots.js` and `setup.js` create or replace in the game folder (the addon, `Inbox.lua`, the slot addons, the ack/sig/act/presence signal files, the migrated SavedVariables file) is now `0777` on macOS and Linux (`bridge/gamefs.js`); Windows is unchanged, and files in `~/.claude-wow` keep their modes. `install-slots.js`, which setup runs, also sets any existing entry under the ClaudeWoW addon folders to `0777`, and `npm run doctor` warns when one is not world-writable.
- Whisper tabs and `/r` no longer taint the game's chat. The addon used to replace every chat edit box's `OnEnterPressed` script and its `SendText`/`SendMessage`/`ProcessChatType` methods, and the `ChatEdit_SendText`/`ChatFrameUtil.SendText` globals, so every line typed ran through addon code and `/cast`, `/gquit` (`GuildLeave`) and other protected commands failed with `ADDON_ACTION_BLOCKED` blamed on ClaudeWoW. Now nothing of the game's is replaced: a whisper to an agent (a whisper tab, `/w Claude ...`) is emptied from the `ChatFrame.OnEditBoxPreSendText` callback, which the game runs through `securecallfunction` after its own slash-command parsing and before the send. The leak filter is unchanged.
- The game context reached Claude once per chat. It went into the system prompt (`--append-system-prompt`), and Claude Code records a conversation's system prompt on its first request and resumes with that record verbatim (`--system-prompt-snapshot`, on by default in 2.1.277), so the position, money and quest log the model saw were the chat's first message's for the chat's whole life: on a resumed chat it kept answering the first turn's coordinates after two moves (measured with `--inject` on a scratch project). The context, and the vision paragraph when a screenshot is attached, now open the message as a marked block (`protocol.messagePrompt`), and the system prompt (`protocol.systemPrompt`) holds only what never changes within a chat, byte for byte: the reply rules, the plugin's lines, the game rules, the map and macro instructions and the primer. That is also the shape prompt caching wants (the stable prefix first, what changes last): the same three turns with the snapshot off, i.e. with the system prompt rendered fresh each request, went from reading 10,243 and writing ~34,000 tokens per turn to reading 44,050 and writing 851. With the snapshot on the cache numbers are unchanged, and the answers are right. The 60% hit rate measured on a live chat had another cause: Claude Code caches with a one-hour TTL, every miss in that chat followed a gap of more than an hour since the previous message, and every message within the hour hit the whole prefix. No CLI flag changes that TTL or places cache breakpoints; `--exclude-dynamic-system-prompt-sections` exists for sharing the base prefix across sessions but does nothing about the per-project part (a `CLAUDE.md` tree of 122k characters was most of that chat's 95k cold tokens; the `ask` plugin's scratch folder starts at ~33k).
- On macOS and Linux the bridge's children (an agent run per chat, the capture script) are now spawned as leaders of their own process groups (`bridge/procs.js`; `detached: true`, which is `setsid` alone: stdio is wired as before and the bridge still waits for them), and ending a run means `SIGTERM` to the group, then `SIGKILL` to the group after `killGraceMs` (new, default 5 s) if anything is still there. Before, `killTree` was a bare `child.kill()` off Windows: an agent that had shelled out (a long `npm test`, a build) left orphans when a run hit `timeoutMs`, the python capture script outlived a SIGINT sent to the bridge pid alone, and a child that ignored the one `SIGTERM` kept its stdout pipe open, so `close` never fired, the chat stayed in `running` and one of `maxParallel` was lost until a restart. A grandchild holding the pipe after the child itself exited is covered too: the escalation is keyed on `close`, not `exit`, and the group is signalled whether or not its leader is still alive.
- The bridge cleans up on its own `SIGINT`/`SIGTERM`: every run and the capture script are ended the same way, each run's `close` handler gets to publish its error to the chat ("The bridge was stopped while ... was still working"), no queued run is started meanwhile, and the bridge exits with the signal's code (130 / 143). The supervisor now waits for the bridge to exit (`SIGKILL` after 10 s) instead of exiting the instant it has signalled it, so Ctrl+C and `claude-wow service stop` strand nothing. `tests/procs_test.js` proves it with children that ignore `SIGTERM`: the escalation, the grandchild case, and the bridge itself under a `SIGTERM` to its pid alone.
- Codex, Claude or Grok installed with `npm install -g` on Windows were not found behind npm's `.cmd` launchers: current npm shims mention `node.exe` before the program, and the bridge took the first path it saw. It now takes the launcher whatever its name (`.js`, `.exe` or a bare script), and honours `agents.<id>.path` pointing at a `.cmd` or `.bat`.
- Professions in the game context were always empty on Forever: the client only has `C_SkillInfo` (one table per skill line), not the classic `GetNumSkillLines`/`GetSkillLineInfo` globals, which stay as fallback. Child lines that repeat their parent are skipped.
- Screenshots no longer pile up while the bridge is down. On the screenshot transport the addon shot on every send (and every retry, and every hello a message typed while disconnected triggered), and only the bridge deletes the file, so a stopped bridge and a player still typing grew the `Screenshots` folder by a full-screen file (about 8 MB as TGA) per message. The addon now stops shooting once the bridge has been silent for as long as its light takes to go red (5 minutes with the presence beats, 22 without), says so once in the game chat and the window, and puts the strip up pixel-style instead so the usual retries and fallback carry the message; it says when shooting resumes, and the Connect button still takes exactly one shot by hand. The bridge sweeps the folder at startup and every 5 minutes: files with the client's screenshot name whose pixels hold a decodable strip (the magic header and checksum only the addon draws) are deleted, files without one, i.e. your own screenshots, are never touched, and files under a minute old are left to the watcher. `/claude-wow diag` shows `screenshots PAUSED` while it is on.
- `screenshotFormat` is given back after a client crash. The addon sets it to `png` (or `tga`) on the screenshot transport and restored the player's value at `PLAYER_LOGOUT`; a crash skips that event, so the player's own screenshots silently stayed in the addon's format. The original is kept in the saved settings from the first change and restored at load too (`ADDON_LOADED`, then `PLAYER_LOGIN`) when the value is still the addon's; a stored original is never overwritten with the addon's own `png`/`tga`, and a format the player set by hand in between is kept as the new original instead of being "restored" over.

## [0.4.0] - 2026-09-24

This release renames the project from **wow-claude** to **WoW AI** (`wow-ai`) and adds two more agents next to Claude Code. Existing installs: `git pull`, `node setup.js` (it migrates the saved data, removes the old addon and updates `config.json`), then quit and relaunch the game. See "Upgrading from wow-claude" in `docs/INSTALL-WINDOWS.md`.

### Added

- **Short replies in the game chat, the full reply in the window.** The system prompt now goes out on every run (game context or not) and asks the agent to end each reply with a `TL;DR:` block of one or two lines; the bridge splits it off (`protocol.splitSummary`) and sends it as `summary` in the slot record next to the full `text`. The new `/wow-ai echo summary` mode, now the default, prints only those lines under `[Claude · chat]` with the `[open]` link to the whole reply; a reply without the block shows its first two lines and a hint to open the rest. Installs that still had the old `full` default saved move to `summary` once; `/wow-ai echo full` brings the old behaviour back.
- **Codex and Grok Build** next to Claude Code. `bridge/agents.js` holds one entry per agent (its command line, how the prompt is handed over, a parser for its output stream), `agent` in `config.json` is the default, and each chat can pick its own with `/wow-ai agent <name>` or the **Agent...** item in the chat's right-click menu (an `agent=` flag on the strip record and in the reload-path outbox). Bubbles, the game-chat echo and the `/r` header name the agent that answered; sessions are kept per agent and folder, so a chat that switches agent starts a fresh session. Per-agent settings live under `agents.<id>` (`permissionMode`, `allowedTools`, `model`, `path`, `extraArgs`; `networkAccess` for Codex). Codex runs `codex exec --json` in a sandbox chosen from `permissionMode`, with the game context at the top of the prompt since it has no system-prompt flag; Grok runs `grok --prompt-file … --output-format streaming-json` with `--permission-mode dontAsk` and the allowlist translated to its globs (headless Grok runs ordinary commands on its own and blocks dangerous ones unless a rule allows them), or `--always-approve`; `deniedTools` adds deny rules for Claude and Grok. Grok's refused tool calls feed the Allow button like Claude's denials; Codex explains a sandbox-blocked command in its own words. Both were tested live against codex 0.156.1 and Grok Build 1.0.41. The banner lists each agent's executable or what to install, `--agent` picks one for `--inject`, and `npm run test:live -- --agent codex` tries one without the game.
- On Windows the bridge unwraps npm's `.cmd` launchers (Codex, or Claude installed with npm) into the script or native binary they run, instead of spawning through `cmd.exe`, and a run that hits `timeoutMs` is killed together with its child processes.
- `docs/AGENTS.md`: per-agent install, command lines, what each permission mode means, limits, and how to add another agent. `tests/agents_test.js` covers the command lines and each CLI's stream format.
- Claude is told which game and client you are on, your character (name, realm, level, race, class, faction, guild), zone and map coordinates, money, talents and professions. The addon sends these few lines with its hello and again when they change (a `c` flag and an extra field in the strip record), the bridge keeps the latest in `state.json` and passes it to every run with `--append-system-prompt`. `/wow-ai context` shows it, `/wow-ai context off` stops it (and clears the bridge's copy), `"gameContext": false` in `config.json` disables it on the bridge side.
- `docs/WOW-ADDON-PRIMER.md`, a short reference on writing addons and macros for the Forever client, goes into the system prompt with the game context on every run, whatever folder the chat works in. `primerFile` in `config.json` points elsewhere or (`""`) drops it; edits are picked up without a restart.
- Shift-click an item, spell, quest or name while the addon's input box has focus to link it into the message, as in the game chat (hooked on `ChatFrameUtil.InsertLink`, the modern chat code the Forever client runs; the old `ChatEdit_InsertLink` global is used only where that is missing). On send, each link becomes `[Name]` in the text and its tooltip is appended in a "Linked from the game" block, so Claude can read an item's stats or a spell's description. Links typed in the game chat (`/ai … [item]`) get the same treatment.

### Changed

- **Renamed to WoW AI.** The addon is `WoWAI` (saved data `WoWAIDB`, slot addons `WoWAI_S###`, signal files under `Interface\AddOns\WoWAI`), the slash command `/wow-ai` (`/ai`, `/ask`, `/wowai` and the old `/wow-claude` are aliases of it, so `/ai agent codex` works; `/claude` is gone; `/r` stays), the bridge command `wow-ai`, the environment variable `WOW_AI_PROJECT`, the repository `chelinho139/wow-ai`. `node setup.js` migrates an install of the old name: it copies the saved data (chats, settings, session token) to `WoWAI.lua`, removes the `WoWClaude` addon and its slot folders, and rewrites `bridge/config.json` (paths, and Claude's `claudePath`/`model`/`permissionMode`/`allowedTools` moved under `agents.claude`). The bridge still reads a config in the old layout. Re-run `npm link` (after `npm unlink -g wow-claude`) and `/wow-ai bind` if you used them.
- A message typed after `/ai` or `/wow-ai` that starts with a command word (`/ai help me write a macro`, `/ai delete the unused imports`) is sent as a message unless the rest of the line fits that command; before, `delete` would have deleted the chat and `help` printed the help.
- Replies are stored with role `assistant` plus the agent that wrote them, in the addon's history and the bridge's `transcripts.json`; older entries with role `claude` are read as Claude's. The `[reply]`/`[open]` hyperlinks in the game chat use the `wowai:` prefix, and the window's cwd line shows the chat's agent.
- Rename and Folder moved off the bottom row into a small menu that opens when you right-click a chat in the left panel.
- Each chat row has a trash can that deletes the chat after an OK/Cancel confirm; `/wow-ai delete` still deletes without asking.
- Send sits at the right end of the input box instead of at the left of the bottom row.
- The bridge no longer exits when the addon folder is missing from `Interface\AddOns`; it logs one warning and the banner shows `addon : NOT INSTALLED`.

### Fixed

- Reload-mode messages now preserve permission grants for the bridge.
- Outbound wire fields now replace record separators inside user text and context.
- State, transcript, and permission-config writes now use the existing atomic writer.
- Agent parser failures now return a bridge error instead of terminating the bridge.
- Windows paths now keep their drive roots in portable protocol tests and progress labels.
- Non-Windows test runs now skip the PowerShell codec check with a clear message.
- Deleting a chat in game now tells the bridge to forget its transcript and agent session (a `d` strip record), so a later restore no longer brings the chat back. Deletions made while the bridge was away are resent with the next hello.
- On clients where the sound-file self-test fails (an empty `.wav` reports as playable), the addon can't hear the bridge's 30-second presence beats, and the status light went yellow 90 s after every reply, so each new message needed a Reconnect click and burned a slot. ## [0.3.0] - 2026-09-22

First public release.

### Added

- In-game chat window (`/wow-claude`) with multiple chats, each backed by its own persistent Claude Code session, running in parallel up to `maxParallel`.
- Outbound transport: messages drawn as a pixel strip in the top-left corner and decoded by a PowerShell screen capture.
- Inbound transport: a pool of 200 load-on-demand slot addons the bridge writes replies into, plus `Inbox.lua` for the `/reload` fallback.
- Empty-wav signal files for acknowledgements, reply readiness, per-action heartbeats, and a 30-second presence beat that drives the status light.
- Live progress in the working bubble: action count, elapsed time, and the files and commands Claude is touching.
- Replies echoed into the game chat; `/r` replies to Claude when it was the last to message you; `/ai <text>` sends from the chat box.
- **Allow & retry** button when Claude is denied a tool, which appends the rule to `allowedTools` and resumes.
- Per-chat working folder (`/wow-claude cd`, **Folder** button) resolved against the bridge's default folder.
- Bridge-side transcripts and automatic restore of chats after the client wipes addon saved data.
- `wow-claude` command (`npm link`) that uses the folder it is started from as the default project.
- `setup.js` installer: finds the client, copies the addon, writes `config.json`, builds the slot pool.
- Test suite: addon in a Lua VM with a stub client, protocol unit tests, slot-file round trip, codec-to-decoder round trip, and a live inject test.
